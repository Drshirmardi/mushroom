# ADR-0038 — Required patient entry separate from medical intake

Accepted by explicit owner instruction,2026-10-21; same F12-FE01 /root.

Entry comprises basic name/date of birth, a specific ADMIN-selected published free assessment, its persisted result and explicit enter-Home action. Medical intake/consent/booking rules remain independent. Basic birth date lives in the entry profile and never fabricates an intake revision or medical consent. Dates are dates, age is derived. Published source must be same-clinic,fa-IR and not commercially governed; schema2 drafts excluded. Do not activate settings or select a real assessment on behalf of owner.

Policy first activation defines an immutable enrollment cutoff for new accounts; existing accounts remain usable. Bound source does not change when the policy selects a newer version; started retired sources may continue, deleted/unavailable sources show an explicit recoverable blocked screen. ADMIN may disable enforcement. An immutable patient completion survives later policy/version changes. Result does not need a decisive type: unresolved educational output still completes entry. Pending results remain visible until explicit completion; closing browser cannot be prohibited, returning resumes saved answers. Guards must protect private patient APIs and App navigation, allowing only entry/auth and exact bound submission operations until complete. Public anonymous catalog and dashboard role authorization are not changed. No automatic clinical/financial approval.

Reuse existing assessment revision/idempotency/answer projection/result engine. Reuse the original UI for ordinary assessment routes; embedded entry mode removes outward exit links and resumes the first unanswered saved question. Transactions/audit/version ownership and source/publication locks protect policy and binding; no new scoring or payment engine. Final scoped unit/integration/type/visual checks; overall feature acceptance remains separate.

## Owner-approved amendment — profile collection independent of assessment (2026-10-24)

After phone verification, every patient account created on or after the profile rollout cutoff must complete first name, last name, profile gender, and birth date before entering the patient app, even when assessment enforcement is disabled or no assessment is selected. The profile cutoff is immutable and independent of the existing assessment enrollment cutoff. The forward migration captures it for existing clinics/policy rows; a clinic created later uses its creation time or the default timestamp on a newly created policy. Accounts predating the cutoff keep their prior eligibility, and an already-started entry remains resumable.

When no registration assessment is required, saving the complete profile releases the entry gate immediately. When an assessment is required, the sequence remains profile → exact selected assessment → saved result → explicit app entry. Missing/unavailable assessments are shown only after profile completion and still cannot be bypassed. Gender uses the existing account-profile field; medical `sexAtBirth`, consent, and intake remain separate and are never inferred or written by this flow. Existing patient-owned assessment and Mezaj provenance/recommendation behavior remains authoritative.

### Corrective owner instruction — supersedes the profile cutoff above (2026-10-24)

The owner explicitly requests fixing all three review findings. Basic profile completeness now applies to existing incomplete accounts too; the proposed profile cutoff is removed in a forward migration, without editing migration history. The assessment enrollment cutoff remains unchanged. Profile-only registration records a durable `completedAt` with no fabricated submission, so later assessment activation does not reopen it. Missing demographics can be repaired during or after an assessment without changing its source, submission, answers, or original completion marker. SQL protects the terminal binding while permitting demographic correction; new completion still validates the required assessment or an eligible profile-only path. Main-database migration is explicitly authorized after backup and disposable upgrade verification.
