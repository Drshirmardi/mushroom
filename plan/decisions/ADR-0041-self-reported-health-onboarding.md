# ADR-0041 — Self-reported health onboarding without a separate consent step

Status: accepted by explicit product-owner instruction, 2026-10-24.

The owner requests a clear patient `/onboarding` flow, reuse of registration details, removal of consent registration from this flow, and fewer dependencies. This amendment supersedes the requirement for a separate processing-consent grant before patient-authored intake storage/completion in ADR-0038 and the engineering standard, only for this self-service workflow.

The mandatory initial registration gate still requires first name, surname, profile gender and birth date. Existing assessment enrollment/pinning rules remain authoritative. Health onboarding starts after that gate and has three steps: three self-reported health declarations, optional lifestyle information, and review/save. It does not patch account details, ask gender again, fetch a consent policy or silently accept a policy. Entry birth date prefills a new health draft; existing medical snapshots take precedence on resume. Existing sex-at-birth answers remain intact; account gender is never converted into a new clinical sex-at-birth fact.

Patient-authored intake draft/finalization and its completion projection no longer require policy availability or a consent grant. Completion requires a real current intake revision, birth date, and explicit allergy/condition/medication declarations; unknown is valid, omission is not. Revision conflicts, idempotency, audit and self-route authorization remain enforced. A forward migration permits a null consent reference on completed PATIENT_ENTRY revisions; operator corrections retain their stronger historical constraint. Historical records are preserved; no grant or patient answer is backfilled.

This decision does not remove separate third-party medical sharing, assessment purchase, couple, or custom-care permissions/consents. Those workflows keep their existing resource/purpose authority. If an exact current processing grant already exists, completion retains its reference for those independently authorized workflows; absence of a policy or grant never blocks self-report completion, and no grant is created implicitly. An intake completion state reports whether the patient's own form is complete, independently of whether a clinician currently has sharing authority.

Account read, phone change and password change retain their exact authenticated routes before initial entry. General patient features remain gated; test fixtures for those features explicitly include completed registration. The patient entry gate refreshes for account/role identity changes rather than token rotation, so a normal session refresh does not discard unsaved form state. API authorization still enforces every request.

Verification: real PostgreSQL no-policy/no-consent self-report completion and ownership/idempotency controls; old feature fixtures/authorization suites; mobile/desktop browser journeys including partial save, optional skip, multiline answers, review, completion and session refresh; generated contract parity and production audit.
