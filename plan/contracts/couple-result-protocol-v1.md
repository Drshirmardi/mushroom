# Couple result protocol v1 — FROZEN

Phase12/F12-PJ-C02, ADR-0025. Prerequisite configuration only, under continuous owner backend implementation authorization. Existing individual WEIGHTED_SUM/v1 engine and qualified physician/source approval remain authoritative. No couple checkout, participant records, private answers, new scoring engine or scientific-validity claim.

One retained CoupleResultProtocolVersion binds an exact questionnaire/hash, current APPROVED AssessmentProtocolReview, independent owner-released same-locale COUPLES_RESULT_SHARING policy/hash, versioned technical APPROVED_PAIR_LOOKUP/v1 and clinician-curated unordered result-band pairs to existing approved G01 educational content. The lookup is deterministic selection, not a fabricated clinical compatibility formula. Only the owner/professional supplies actual pair associations and disclosure wording. No compatibility percentages, diagnoses, therapeutic diets or default sixteen-type taxonomy. Consultation recommendation is a boolean per pair; service selection continues through existing directory.

Definition: assessmentVersionId, protocolReviewId, disclosurePolicyVersionId, pairs[{firstBandId,secondBandId,guidanceContentIds[1..5],recommendConsultation}]. Source order normalizes unordered pairs, rejects duplicate/reversed duplicates, unknown IDs and empty content. Source1..32 result bands, no requiresReview band until actual review workflow; max528 pairs, max50 distinct approved content versions, same clinic/locale, hash-pinned references and bounded retained JSON. Drafts may omit pairs; approval requires exhaustive n(n+1)/2 distinct unordered pair coverage. No default case, inferred recommendation or fallback on missing mapping. Content provides existing provenance/approval/safety boundaries.

ADMIN with existing ASSESSMENTS_MANAGE and explicit live same-clinic access may append idempotent immutable DRAFT versions and read them; can retire only unapproved drafts. Only current linked active published same-clinic DOCTOR with current clinical-sign capability and owned live session may approve/revoke approved definitions. Approval requires exact contentHash, educationalOnly:true, noDiagnosisOrTherapeuticDiet:true and reviewedJointDisclosure:true. DRAFT→APPROVED→REVOKED or DRAFT→REVOKED only; final revocation, no edits/delete/reactivation. Existing authority, consent release, protocol, content, hashing, audit and Prisma reused. Stable scoped errors, metadata-only atomic audits and private/no-store APIs.

Internal usable(tx,clinicId,assessmentVersionId,exactId?) validates current exact source/protocol/processing and disclosure policies, current physician qualifications and all pinned content dependencies; optional locking stabilizes them for later transactions. Default chooses latest ever-approved version and never falls back past revocation/dependency loss; a newer unapproved draft does not replace approved version. Exact pins remain distinct for future immutable purchase/result evidence and can never be silently rebound. Readiness reports concrete blockers; missing actual legal/content configuration remains closed.

Eight operations/eight paths: admin/couple-result-protocols POST versions, GET list, GET :id, POST :id/revoke; clinical/couple-result-protocols GET list, GET :id, POST :id/approve and POST :id/revoke. Bounded pages1..50, source/status filters; no patient endpoint or patient/partner data. Receipt/attempt/joint result access remains a later task with independent mutual consent and purpose-specific ownership. Linking consent alone never grants processing/disclosure. Future joint projection must expose only approved joint educational content, never participant-specific answers/scores/band labels; consent withdrawal blocks joint access without ordinary refund or erasing financial evidence.

Acceptance: actual PostgreSQL draft→qualified approve→current readiness→final revoke; exhaustive pair validation/canonical idempotency/immutable version race; source/hash/policy/content/reviewer changes fail closed with no old fallback; strict DTO/roles/live session/clinic isolation; direct SQL lifecycle/sequence/author/approval/session evidence, no mutation/delete; atomic audit failure; fresh/additive populated migration preservation/no drift; focused individual purchase/protocol/content/couple regressions, generated API/client and consumer types. No actual source/legal/clinical associations seeded or live provider/persistent DB/UI change.
