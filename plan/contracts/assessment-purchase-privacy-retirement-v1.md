# Assessment purchase privacy retirement addendum v1 — FROZEN

F12-PJ-P02, ADR-0024, additive to assessment-purchase-access-v1. Review reproduced an unfinished paid attempt blocking a later explicitly reconsented purchase after final privacy withdrawal (409 from active-attempt guard). Old evidence must remain and must never be rebound/revived.

In the same consent-withdrawal transaction, retain the exact processing withdrawal then move only that patient's still-IN_PROGRESS attempts bound to that consent to existing INVALIDATED state. Increment revision, set monotonic invalidatedAt/updatedAt, retain answers/score/source/grant/start/completion evidence unchanged. Completed attempts remain unchanged and inaccessible through withdrawn access. Idempotent withdrawal can reconcile any unfinished bound attempt without rewriting old withdrawal evidence. This retires processing context, not financial purchase; no refund, deletion, old consent reactivation or grant reuse. New explicit consent and new successful purchase create a different grant/attempt under the existing engine/active-attempt constraint.

Paid save/submit acquire the same per-patient assessment-consent namespace before attempt row locking, so withdrawal→attempt invalidation cannot deadlock against attempt→consent writes. SQL permits only this exact metadata-only final privacy transition when the bound processing consent is actually withdrawn; unrelated writes still require currently processable exact access. Paid attempts cannot be deleted, including unfinished ones, because retained one-attempt-per-grant consumption must survive. Legacy null/free deletion behavior unchanged. Applied migration50 is never edited; a forward migration51 refines the context guard and adds paid-attempt retention.

Acceptance: reproduce pre-fix409; new consent/new purchase after withdrawal succeeds with a distinct grant/attempt and old answers/source/grant retained; old grant remains unusable; withdrawal/autosave race serializes without deadlock; audit failure rolls back consent and attempted invalidation; SQL rejects disguised answer mutation and deletion/reactivation/rebinding. Retention/deletion under actual approved legal policy remains an external owner/operator workflow, not invented automatic erasure.
