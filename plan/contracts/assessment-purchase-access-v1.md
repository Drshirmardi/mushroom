## Purchase, consent and financial boundaries

New ASSESSMENT billing purpose, explicit ASSESSMENT_PURCHASE reservation effect/FK, immutable AssessmentPurchase tariff/consent snapshot and AssessmentAccessGrant per independently identified beneficiary. Current slice issues one INDIVIDUAL grant only; schema does not pre-authorize a second participant. Positive configurable integer IRR/PRE_START, min18 from existing current self-reported intake birth date; do not demand unrelated sensitive intake fields. No ordinary successful assessment refund/cancellation. Store/appointment rules unchanged. Pending unpaid bank intents may be abandoned/cancelled as financial intents; no paid assessment cancellation. Expiring quote uses configured draft quoteTtlSeconds or technical900seconds default, distinct from nonexpiring invitations and nonexpiring paid access.

Before purchase the patient independently accepts exact active same-clinic processing and purchase-terms policies via existing PatientConsentRecord, owned active session, explicit accepted:true and contentHash. No intake/account-link consent implication. Record reuse is per patient/exact policy; canonical key replay never reactivates withdrawn consent, new explicit acceptance creates separate evidence. Processing withdrawal remains possible after policy retirement, stops grants bound to that exact record and causes no ordinary refund; later acceptance never revives old grant. Purchase terms acknowledge a retained contract; no terms-withdrawal-as-refund endpoint. Actual legal/clinical text is owner supplied, never seeded as real approval.

Prepare/reserve under per-patient/questionnaire serialization recheck current clinical/commercial source, adult identity and exact unwithdrawn consent. Prevent a second unresolved pending purchase or unused grant for the same individual source; original command replay returns existing intent. One paid grant starts one owned attempt, same grant retries resume the same attempt; no sharing/rebinding/extra attempt. Existing one-active-attempt constraint remains. A price replacement preserves existing unexpired quotes against its immutable tariff; explicit commercial withdrawal or clinical/consent change blocks settlement. Bank Verify success that cannot fulfill, late or duplicate captured funds follow existing traceable wallet compensation, not ordinary assessment refund; never grant access on a callback hint/failed/abandoned intent. WALLET debit and grant issuance are atomic; GATEWAY requires exact server-verified amount/order/attempt. Deferred SQL proof validates final paid intent and immutable journal or verified noncompensated attempt at commit, because shared dispatcher settles domain before final PAID/VERIFIED updates. PAID intent must have its exact one grant; no manual paid flip, FREE method, cross-patient grant or ordinary BillingRefund. No live Sadad acceptance claim.

No diagnosis/therapeutic diet or scientific-validity claim.

## Additive API

PATIENT/self-only with existing assessment and wallet permissions, live patient role/session/user/active clinic; all private/no-store and transactional metadata audit. No request patient/clinic override, price, algorithm or status fields.

- GET /v1/patients/me/assessment-offerings?page&pageSize: bounded active commercial metadata; detail validation required, no questions/private reviewer data.
- GET /v1/patients/me/assessment-offerings/:publicationId: exact currently available tariff, fixed policy, exact processing/terms bodies+hashes and patient's acceptance references; explicit purchaseSupported/blockers for couples/clinical-review gates. No entitlement from reading.
- POST /v1/patients/me/assessment-consents: Idempotency-Key; policyVersionId,contentHash,accepted:true.201 retained projected record. POST /:id/withdrawal for owned processing consent with same key discipline; final privacy withdrawal, not cancellation/refund.
- POST /v1/patients/me/billing/assessment-intents: Idempotency-Key; publicationId,publicationHash,processingConsentRecordId,termsConsentRecordId.201 existing BillingIntentDto with additive nullable assessmentPurchaseId. Existing wallet/gateway/intents/payment-result flow reused.
- GET /v1/patients/me/assessment-purchases?page&pageSize and GET /:id: own retained receipt/intent state/tariff/owned grant/attempt references, no raw answers/results. One billing intent per immutable purchase.
- POST /v1/patients/me/assessment-access-grants/:id/submission: explicit start/resume after payment,201 existing submission DTO. Existing save/submit/result/guidance routes then operate on that exact owned attempt.
