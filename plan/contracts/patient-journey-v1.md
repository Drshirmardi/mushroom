# Patient Journey v1 — additive backend contract

Frozen 2026-10-16 for F12-PJ-J01 under explicit continuous backend implementation authorization. Existing contracts remain unchanged. This is read composition over existing modules, without journey persistence or a new state machine.

GET /v1/patients/me/journey requires PATIENT and existing self-profile/intake/assessment/appointment/commerce/wallet/content read permissions. Identity and clinic derive exclusively from the active session's patient. Response is private/no-store. Missing patient returns existing 404; database/audit failures never become a fabricated empty success.

Return evaluatedAt, onboarding requirements/progress (derived, no medical values), authoritative bookingEligibility, nextAction, bounded recent active/completed assessment summaries, relevant appointments, pending billing intents, pending Store orders and published active/completed treatment-plan references. Each collection is at most five items with hasMore; callers use existing domain list/detail APIs for full data. IDs are opaque references; no raw answers, scores, result text, names, contact details, payment credentials, raw snapshots or clinician drafts. Billing money is integer string with explicit IRR; orders retain explicit TOMAN to avoid unit confusion. Expired intents are excluded even before reconciliation. No entitlement is inferred from a pending payment or existing treatment plan.

Priority: current/near appointment (starts within 15 minutes, CONFIRMED through one hour after end; CHECKED_IN/QUEUED/IN_PROGRESS through four hours after end) → incomplete onboarding using existing action → booking assessment requirement → resumable published active attempt → live pending billing intent → published treatment plan → latest valid completed result → book consultation. Appointment action opens its existing detail; it does not grant chat/start permission. Detail/chat/booking/payment commands always reauthorize current state. Retired drafts are discoverable with resumeAvailable=false and VERSION_NOT_PUBLISHED until the historical-questionnaire discovery extension; existing submission commands retain their previous behavior. They never silently switch questionnaire version. No new algorithm or result-release assertion is implied by a completed legacy summary.

Onboarding and domain projections are read in one repeatable-read transaction, followed by sensitive PatientAccessAudit READ in that transaction. Audit metadata contains counts/view only. No patient provision, conversation creation, payment reconciliation or other domain mutation occurs. A first registration must use the existing profile provision flow before this endpoint. Store shopping is independently available to authenticated patients and does not depend on medical onboarding; consultation eligibility retains existing policy. New digital offerings/couples/guidance are not advertised until their implementation and approvals exist.

Acceptance: unauthenticated/other-role and revoked-session refusal; patient/clinic isolation; genuine incomplete/complete/retired states; deterministic action priority; expired/terminal exclusion; bounded lists/hasMore; explicit money; secret/draft exclusion; no domain writes; fail-closed audit; official additive OpenAPI/client and existing consumer type compatibility. No frontend or production acceptance claim.
