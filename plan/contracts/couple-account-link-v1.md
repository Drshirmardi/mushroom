# Couple account-link v1

Frozen 2026-10-16, F12-PJ-C01 / ADR-0020. Implements owner age18 and no automatic invitation expiry; does not implement purchase cancellation, clinical couple assessment or answer sharing. No existing frozen contract is changed.

PATIENT + ASSESSMENTS_READ_SELF for reads, ASSESSMENTS_WRITE_SELF for commands; additional existing intake self permission for age-check commands. Active session plus resource/patient/clinic ownership on every operation. Private/no-store responses. Reuse existing PostgreSQL rate limiter for authenticated user reads120/min, commands30/min. Tokens stay in POST body/initial response, never query/path/access logs. No external messaging.

Routes under /v1/patients/me:
- GET couple-link-policy: current active same-clinic COUPLES_ACCOUNT_LINKING/fa-IR policy identity/title/body/hash/version; missing policy503.
- POST couple-sessions, Idempotency-Key, { consentPolicyVersionId, consentAccepted:true }: adult initiator explicitly accepts current policy; create session+INITIATOR participant+audit atomically. Key/payload replay preserves the existing session; changed consent key conflicts. Policy pin and consent evidence are immutable.
- GET couple-sessions?page=1&pageSize=20 (page<=10000/pageSize<=50), GET couple-sessions/:id: owned same-clinic link summaries, at most two slots with isSelf/consent state, never partner id/name/phone/medical values. assessmentReady:false until the future assessed-offering/access/clinical contract exists.
- POST couple-sessions/:id/invitations, Idempotency-Key, { recipientPhone }: initiator only, awaiting partner, own consent intact; normalize with existing identity utility; require registered same-clinic recipient distinct from self. Bind by recipient patient id without copying phone. New key explicitly replaces/revokes an earlier pending invitation. Return invitationId/sessionId/status/expiresAt:null/invitationToken only on first creation; key replay returns same resource/status with token:null. Token is43 base64url characters from random32 bytes; stored hash only. Unknown/ineligible target gets the same generic422, no public identity lookup endpoint.
- POST couple-invitations/preview { invitationToken }: intended authenticated recipient only; read pinned policy and safe session reference without consuming/changing anything. Retired/current-policy mismatch409 requiring updated consent flow, no automatic expiration. No grant/acceptance from link opening.
- POST couple-invitations/accept { invitationToken, consentPolicyVersionId, consentAccepted:true }: intended independently authenticated adult account only, exact pinned/current policy, session awaiting partner, initiator consent intact; create unique PARTNER participant and accept invitation/link session once under session lock. Identical accepted recipient replay returns linked session; never grants access to another account. Two accepted participants maximum.
- POST couple-sessions/:id/consent-withdrawal: own accepted participant only; idempotently append withdrawal timestamp, mark session CONSENT_REVOKED and revoke pending invitation. No answer/result disclosure, purchase cancellation or financial mutation. No regrant on a revoked session in this contract.

Age check reuses current intake birth date and UTC date age calculation; missing/future/under18 date blocks own joining with422 COUPLE_PARTICIPANT_INELIGIBLE, no duplicate DOB collection or legal verification claim. Both participants consent through their own principal; there is no proxy/shared-account mode. Session starts AWAITING_PARTNER, then LINKED or CONSENT_REVOKED. Only linking consent exists in this slice; medical processing, individual response privacy, commercial entitlement and joint result approval need their later dedicated contracts and must not infer permission from LINKED.

Persistence: same-clinic session/participants/invitations FKs; unique(session,slot), unique(session,patient), at most one pending invitation/session; immutable creator/key/hash/policy/age and participant consent identity; only monotonic acceptance/revocation transitions. Session/invitation idempotency namespaces scoped to initiating patient; command hashes canonical and no raw keys/tokens/phone in read DTO/audit. Session+consent write and audit atomic; sensitive read audit mandatory. One-time secret loss recovery is explicit replacement, not raw-token persistence. Invitations lack a deadline and remain valid until accepted or explicitly superseded/revoked; privacy/identity/consent checks always apply.

Existing consent CLI defaults remain MEDICAL_INTAKE_PROCESSING. New key is accepted only with explicit CONSENT_POLICY_KEY=COUPLES_ACCOUNT_LINKING and a matching environment-approved, hash-valid owner document/release reference. Never seed/publish actual legal text in this task. Missing production policy is a real activation blocker, not a fake empty success. Stable errors: COUPLE_SESSION_NOT_FOUND, COUPLE_INVITATION_NOT_FOUND, COUPLE_INVITATION_UNAVAILABLE, COUPLE_PARTICIPANT_INELIGIBLE, COUPLE_POLICY_UNAVAILABLE, COUPLE_CONSENT_POLICY_CHANGED, COUPLE_STATE_CONFLICT, COUPLE_RATE_LIMITED; reuse FORBIDDEN/IDEMPOTENCY_KEY_REQUIRED/IDEMPOTENCY_KEY_REUSED/VALIDATION_ERROR.

Acceptance: authenticated adult boundary (including eighteenth birthday) and self-reported-age limitation; exact independent consent/version/clinic; raw token hashed/one-time response and no read/audit leaks; registered target identity, foreign/self/third-party/third-slot denial; old token remains valid without deadline; preview does not mutate; create/issue/accept/withdraw/replacement races and replay, audit rollback/failure; FK/unique/immutable SQL constraints; derived Journey minimized links;44→45 legacy preservation/fresh replay/no drift; official generated contracts and focused regressions. Real owner consent publication, frontend links/browser acceptance, clinical processing, paid assessment and live provider acceptance remain separate.
