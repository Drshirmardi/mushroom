# Assigned physician consultation operations v1 — FROZEN

Phase12/F12-PJ-D02, ADR-0029; depends on accepted D01/C04 and existing appointment/encounter/clinical/text-chat contracts. Continuous owner implementation scope includes consultation/doctor workflow. Add a narrow assigned-physician facade; no new booking, payment, consultation session, realtime engine, role/default capability, clinical review or legal data.

GET /v1/clinical/appointments returns a bounded assigned worklist; GET /:appointmentId/consultation-context returns minimal same-appointment operational context. Current linked active published same-clinic DOCTOR with published specialty/current clinic membership/sign qualification and explicit current DOCTOR-role CLINICAL_RECORD_VIEW is required. Patient/ordinary ADMIN/STAFF and another same-clinic doctor cannot impersonate. No arbitrary doctor/clinic/patient filters. List page1+,pageSize1..50; optional status and UTC ISO from/to, max93day range, default now−4hours..now+31days and nonterminal states. Row ownership always derived server-side. No cross-patient history, intake, raw assessments, diagnosis, internal note, price/payment/wallet/invoice, phone/email/DOB or medical consent exposed. Minimum assigned-patient display name, patient/appointment/service identifiers, service name, visit mode/time/status and encounter id/state are permitted for the established appointment relationship; disabled patient/clinic/actor is unavailable. Reads are audited per affected patient in one bounded bulk insert, fail-closed without N+1 audit round trips.

Context adds canStart/canComplete based on real current own edit permission, appointment/encounter/doctor-busy state and existing consultation window; canOpenAssessmentContext is only existing D01 current authorized-share readiness. Text support is ONLINE only, with an existing conversation reference if any; GET creates no conversation/message/encounter/consent. Voice/video support is explicitly false. Existing Chat REST/waiting-room/window/block/session logic remains the authority for actual text use; this facade confers no message permission or clinical source access.

POST /:appointmentId/start and POST /:appointmentId/complete require the same current qualified assigned physician plus explicit current DOCTOR-role CLINICAL_RECORD_EDIT and VIEW; existing sign qualification remains. No nonempty request body, target patient/doctor/status/source/price override or appointment-management capability. Use current independent live session/clinic/role/permissions/assignment under the same transaction as existing mutations. Existing checked-in/queued→IN_PROGRESS+Encounter and IN_PROGRESS→COMPLETED+Encounter workflows, actor status history and operational activity are reused. No payment, booking eligibility, check-in/queue ownership, cancellation/rescheduling/refund or clinical-note publication policy changes. Old admin routes preserve their authorization/contracts and responses.

Stabilize shared operations with doctor advisory lock then exact appointment row lock/re-read before authorization/mutation. This also fixes stale concurrent existing admin start/complete retries, without adding duplicate state. New assigned authorizer runs after locks. Same-target repeated start/complete returns the existing result without duplicate encounter/status history/activity; two different starts for the same doctor remain mutually exclusive. Reassigned/cancelled/closed appointment cannot be authorized by a stale preflight check. Existing source/clinical/privacy gates remain independent. Start and first completion are allowed only from startsAt−15m through endsAt+4h for operational visits; incomplete future/expired/PENDING/CONFIRMED/terminal transitions fail. Completed repeat is an authorized no-op even after the window. Mutations and real actor/session metadata-only clinical audit commit atomically; audit failure rolls back all existing appointment/encounter/history/activity effects. Mutation response is the same minimized context, never the raw administrator financial projection. State-idempotent existing transitions require no new command journal or billing operation.

Implementation reuses internal transaction-aware start/complete seams in AdminAppointmentsService exported through existing module; old wrappers call those seams without new assigned authorization. The assigned facade supplies its mandatory in-transaction authorizer and has no unguarded public operation. ClinicalAccessAuditService adds bounded recordMany without changing existing single-event semantics. New assigned module/DTO/controller/service, narrow module exports/shared seams/app/error wiring, focused tests/generated contracts/CI/governance only. No schema/migration is expected.

Acceptance: actual independently authenticated assigned doctor worklist/context→existing operator check-in/queue→new start→single existing encounter→text/in-person operational context→new completion; no implicit assessment disclosure and no text/audio/video infrastructure claim. Deny patient/admin/unassigned/foreign clinic/disabled/unlinked/unpublished/session/current role/view/edit/sign loss, strict query/body/no financial/PII/medical data leakage; timing/state/busy gates; same-target/different-target/admin-vs-assigned concurrency and stable repeat; locked assignment/state authorization; no create on GET; patient-specific bulk audit and read/write/audit rollback; focused existing booking/billing/encounter/chat/D01/C04 regressions, official additive API/client/consumer types/main review/evidence/independent commit. Actual capability/legal/clinical/frontend/provider acceptance remains external; later clinical review and program delivery rules stay separate.
